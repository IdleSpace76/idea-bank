# Работа с Idea Bank

Idea Bank представляет собой личную библиотеку идей на Next.js, React и TypeScript. Локальная версия (`npm run local`) сохраняет SQLite и вложения в `data` внутри приложения, облачная использует GitHub для входа, Vercel для приложения и закрытый Backblaze B2 для библиотеки и медиа. Между версиями данные переносятся через ZIP. Каждый облачный экземпляр рассчитан на одного владельца.

## Развёртывание по запросу пользователя

Прочитайте [сценарий для агента](docs/agent-deployment.md), затем [руководство по настройке](docs/deployment.md). Выполняйте доступные действия самостоятельно, подключайте пользователя только там, где нужны его вход, согласие или недоступные агенту действия. Не начинайте развёртывание при обычной работе над кодом.

Инструкции пользователя и правила его рабочего пространства определяют границы разрешённых действий. Учитывайте уже полученное разрешение; не запрашивайте повторное подтверждение каждого действия внутри согласованного шага.

## Работа с кодом и данными

- Перед изменениями проверьте состояние Git. Сохраняйте чужие правки и рабочие настройки.
- Не выводите секреты из `.env.local`, настроек хостинга или ответов инструментов. Не добавляйте их в код, чат и отчёты.
- Не публикуйте пользовательскую библиотеку и вложения. Стартовый пример и изображения документации не являются личными данными владельца.
- Не заменяйте библиотеку, не выбирайте направление первой синхронизации и не разрешайте конфликт без решения владельца.
- Для публичного облачного сайта обязателен `IDEA_BANK_AUTH_MODE=github`. Режим `local` предназначен для локального запуска.
- `local`, `local:start` и `runIdeaBank.cmd` принудительно выбирают дисковый режим; `dev` и `start` учитывают переменные окружения. Не используйте локальные скрипты для проверки GitHub-входа. `github` без B2 не подтверждает настройку облачной библиотеки. Папку дисковых данных не связывайте с облаком: перенос выполняется только через ZIP по решению владельца.
- Локальный STDIO и облачный HTTP MCP подключаются независимо. Наличие реализации в коде не разрешает менять настройки MCP-клиента, подключать библиотеку или проходить авторизацию без запроса владельца. Перед ручным копированием `data` остановите веб-сервер и все локальные MCP-процессы этой библиотеки.

## Проверки

MCP описан в `docs/mcp.md`. Изменения через агента проходят через `LocalAgentBackend` или `CloudAgentBackend`, без обхода версий и квитанций повторов. Не подключайте личную библиотеку к интеграционным тестам. Основные проверки: `test:mcp`, `test:mcp-auth`; после сборки `test:mcp-http`. `test:mcp-codex` отдельно запускает настоящий Codex с существующим входом и расходует его лимит. Облачный MCP выключен без `IDEA_BANK_MCP_ENABLED=true`; секреты приложения не передаются клиенту.

Для дискового режима используйте `test:disk-storage`, `test:local-launch`, `test:disk-api` и `test:local-migration`. `test:disk-api` и `test:local-migration` требуют готовой сборки и сами выбирают изолированные порты и временные папки, без пользовательской `data`.

Команды выполняются из корня с `package.json`:

```sh
npm ci
npm run typecheck
npm run build
npm run source:check
```

`npm ci` нужен при первой установке, изменении зависимостей или смене версии Node.js для нативного драйвера SQLite. По характеру изменений используйте `test:auth`, `test:storage`, `test:catalog`, `test:reader`, `test:sync`, `test:scoped-sync`, `test:auto-sync` и `test:sync-events`. `test:sync` проверяет переход и совместимость, `test:auto-sync` и `test:scoped-sync` проверяют очередь и события. Браузерные тесты используют Microsoft Edge. Не запускайте проверки с пользовательскими данными и не занимайте порт работающего приложения без согласования.

`test:e2e` содержит сценарии прежнего браузерного локального хранилища и требует адаптации для SQLite; он не заменяет дисковые наборы выше. Его `PLAYWRIGHT_BASE_URL` задаёт адрес сервера, но не изолирует папку данных. Не запускайте весь этот набор против дисковой пользовательской библиотеки.

После изменений чтения, записи, кеша или синхронизации запускайте `npm run test:requests` после сборки. Сохраняйте бюджеты из `docs/b2-storage.md`: локальные переходы и открытие форм без облачных запросов, отправка только изменений, один пакет по событию и одна сверка при штатном восстановлении сети. Не отключайте проверки версий, повтор после потери ответа или разрешение конфликтов ради сокращения запросов.

Для документации проверяйте ссылки и соответствие команд проекту. Описывайте результат и непроверенные части отдельно; успешная сборка сама по себе не подтверждает вход и синхронизацию.
