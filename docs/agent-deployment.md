# Развёртывание с помощью ИИ-агента

Сценарий предназначен для агента, которому пользователь поручил развернуть личный Idea Bank. Агент выполняет доступную техническую работу и проводит владельца через действия, требующие его участия.

Поля сервисов, команды и переменные описаны в [руководстве по развёртыванию](deployment.md). Используйте его как основной источник настроек. Если интерфейс сервиса изменился, сверяйтесь с его официальной документацией. Не подменяйте неизвестные значения предположениями.

## 1. Определите исходное состояние

Прочитайте правила рабочего пространства и `AGENTS.md`. Проверьте `git status`, адрес репозитория, `package.json`, `.env.example` и наличие установленных зависимостей. Не выводите содержимое `.env.local`.

Через доступные инструменты выясните, какие ресурсы уже созданы: форк, проект Vercel, GitHub App для входа и bucket B2. Отсутствие подключения к аккаунту не означает, что ресурсов нет. Уточните это у владельца перед созданием повторных ресурсов.

Кратко обозначьте текущий шаг, что будет настроено и где требуется участие пользователя. Соблюдайте согласованный порядок работы. Если разрешение ограничено одним шагом, завершите его и согласуйте следующий.

По умолчанию используйте личный Vercel Hobby и B2 без карты, платных дополнений и покупки домена. Перед созданием ресурсов проверьте актуальные условия бесплатного использования. Если сервис требует платёжный метод, остановите этот шаг и сообщите владельцу: согласие на развёртывание не разрешает расходы.

## 2. Выберите доступный способ работы

Используйте подключённые инструменты сервисов, затем авторизованный CLI или доступный браузер. Дополнительный плагин не обязателен. Не требуйте его установки, если задача решается существующими средствами.

Выполняйте настройку через доступные средства в пределах разрешения пользователя. Если действие недоступно, подготовьте точные значения полей и дайте владельцу один короткий шаг. После его ответа проверьте результат и продолжайте.

Регистрация, вход в аккаунты, двухфакторная проверка, CAPTCHA и выдача разрешений остаются за владельцем, если требуют его участия. Не запрашивайте пароли, коды подтверждения или доступ к чужим аккаунтам. Не обещайте обойти ограничения сервиса.

Для каждого ручного шага укажите:

- страницу и нужную кнопку;
- значения полей и разрешения;
- признак успешного завершения;
- что сообщить агенту, не раскрывая секретов.

Не выдавайте всю настройку несколькими длинными списками сразу. Не повторяйте уже выполненные шаги.

## 3. Подготовьте репозиторий и хранилище

Следуйте разделам 1 и 2 [руководства](deployment.md).

Используйте форк владельца или его существующую копию. Не перенаправляйте Git remote и не отправляйте изменения в исходный репозиторий разработчика. Не перезаписывайте рабочую папку и локальные настройки. Установите зависимости при необходимости, проверьте типы и сборку.

Создайте или проверьте закрытый bucket B2 с шифрованием и сохранением версий. Ключ должен быть ограничен этим bucket и иметь необходимые права для объектов и настройки CORS. Не используйте master key. Не меняйте правила хранения и не удаляйте существующие объекты.

## 4. Настройте вход владельца

Следуйте разделам 3 и 4 руководства. Собственная GitHub App отвечает за вход в Idea Bank; интеграция Vercel с GitHub отвечает за получение кода. Не смешивайте эти подключения.

Проверьте Client ID, Client secret и числовой GitHub ID владельца. App ID, логин и `node_id` не заменяют нужные поля. Private key и PEM для этого способа входа не требуются. Не запрашивайте доступ к репозиториям у приложения для входа.

Используйте `.env.example` только как шаблон. Существующий `.env.local` дополняйте без перезаписи рабочих значений. Секрет сессий генерируйте криптографическим генератором и передавайте сразу в защищённое место назначения, без вывода в лог или чат.

Если безопасная передача секретов через инструменты недоступна, попросите владельца самостоятельно заполнить `.env.local` или переменные Vercel. Получите подтверждение заполнения, а не сами значения. Секреты не должны попадать в аргументы команд, историю терминала, скриншоты, Git или клиентские переменные `NEXT_PUBLIC_*`.

## 5. Разверните приложение

Следуйте разделам 5–7 руководства.

До первого публичного развёртывания задайте `IDEA_BANK_AUTH_MODE=github` для Production и Preview. Не публикуйте приложение с режимом `local`, в том числе временно для диагностики.

Проверьте владельца проекта Vercel, репозиторий, production-ветку, корневую папку и Next.js preset. Для доступа Vercel к GitHub достаточно выбранного форка. При существующем проекте продолжайте его настройку вместо создания дубликата.

После первой сборки найдите постоянный production-домен в настройках проекта. Используйте его для `AUTH_URL`, callback GitHub App и CORS. Адрес отдельного deployment не подходит для постоянной настройки.

Перенесите все переменные из таблицы раздела 7 в Production, проверьте их наличие без вывода значений. Для production создайте отдельный `AUTH_SECRET`. Не копируйте рабочие секреты в Preview автоматически: до отдельной настройки Preview должен оставаться закрытым.

После изменения переменных выполните новое production-развёртывание и дождитесь Ready. Не меняйте настройки других проектов и доменов владельца.

Если владелец выбрал уведомления об изменениях, выполните [настройку Ably](deployment.md#уведомления-об-изменениях-необязательно). Используйте Free без карты, отдельное приложение и ключ с Publish/Subscribe только на `idea-bank:sync:*`. Передавайте ключ в Production как Sensitive `ABLY_API_KEY`; не копируйте его в Preview или публичные переменные. Ключ не должен появляться в чате, аргументах команд и логах. Если безопасный перенос недоступен, владелец вводит его в Vercel сам. Ably не хранит библиотеку; уведомления содержат только версии и идентификаторы изменённых записей. Пакеты сверяются с локальной контрольной точкой; не добавляйте периодическое перечитывание каталога или полных идей. Страховочная проверка B2 выполняется раз в 10 минут, в том числе без Ably.

## 6. Настройте CORS

Следуйте разделу 8 руководства. Используйте существующий `storage:cors`: без `--apply` он проверяет настройки, с `--apply` добавляет origin в правило приложения, сохраняя остальные правила и закрытый доступ.

Передайте production `AUTH_URL` только на время команды. Если переменная окружения уже задана в текущем процессе, сохраните и восстановите её прежнее значение в `finally`; если отсутствует, после команды удалите её. Не заменяйте локальный адрес в `.env.local` ради этой операции.

Проверьте настройки повторно без `--apply`. Не открывайте bucket для публичного чтения и не разрешайте все origins для устранения ошибки.

## 7. Проверьте результат с владельцем

Сверяйтесь с разделами 9 и 10 руководства. Отмечайте отдельно проверки агента и подтверждения пользователя.

| Проверка | Ожидаемый результат |
| --- | --- |
| Production deployment | Ready, подключён нужный репозиторий и ветка |
| Постоянный HTTPS-адрес | Приложение открывается без ошибки соединения |
| Без активной сессии | Библиотека закрыта, доступен вход |
| Вход владельца | Библиотека открывается, доступны выход и синхронизация |
| Контроль доступа | `IDEA_BANK_OWNER_ID` соответствует владельцу, режим `github`; проверки `test:auth` проходят |
| B2 и CORS | Bucket закрыт, правило разрешает точный production-origin |
| Первое подключение | Чистое устройство автоматически получило облачную библиотеку; при наличии собственных локальных идей источник выбрал владелец |
| Порционная загрузка | На чистом втором устройстве получены разделы и первые карточки; прокрутка загружает следующие, открытие идеи получает её блоки; закрытые идеи не скачиваются целиком |
| Кеш и офлайн | Повторный переход использует кеш без нового запроса; события и контрольная проверка получают изменения в фоне. Без сети просмотренная идея отмечена как офлайн-копия, неполученная идея запрашивает соединение |
| Автоматическая синхронизация | Сохранённая правка отправлена без нажатия кнопки; после возврата к первому устройству получена там |
| Уведомления Ably, если подключены | Две видимые вкладки на разных устройствах получают согласованную правку без возврата фокуса и ручной проверки; ключ не доступен браузеру |
| Состояние отправки | После проверки отображается «Сохранено в облаке», нет нерешённого конфликта или запроса входа |

Не запускайте тесты против рабочей библиотеки. Проверки кода выполняйте на изолированных тестовых данных. Вход другого GitHub-аккаунта проверяйте только при наличии разрешённого тестового аккаунта; если его нет, не выдавайте эту проверку за выполненную.

Перед переносом существующих идей предложите ZIP-копию. На чистом устройстве приложение само получает облачную библиотеку; если облако ещё не инициализировано, сохраняет стартовый Example. При наличии собственных локальных идей источник, замену библиотеки и выбор при конфликте определяет владелец после просмотра данных. Не отправляйте стартовый Example поверх облачной библиотеки. Для проверки переноса используйте согласованную небольшую правку или пример, сохраняя существующие материалы.

Для существующей библиотеки старого формата используйте раздел [перехода](b2-storage.md#сохранность-и-обновление-старой-библиотеки). Сначала сохраните ZIP и обновите все устройства. Не нажимайте переход, не выбирайте источник и не разрешайте конфликт за владельца. Старые сборки после перехода не могут записывать облачную библиотеку.

Проверки кода: `typecheck`, `build`, `test:auth`, `test:storage`, `test:catalog`, `test:reader`, `test:sync`, `test:sync-events`, `test:auto-sync`, `test:e2e`, `source:check`. `test:sync` проверяет совместимость и переход; `test:scoped-sync` проверяет текущую очередь. После изменений запросов выполните `test:requests` на готовой сборке: suite проверяет бюджеты B2 и HTTP, брокер, восстановление сети и очистку. Для E2E задайте свободный изолированный порт через `PLAYWRIGHT_BASE_URL` и режим `local`; не используйте порт работающего пользовательского сервера. Реальный OAuth, B2 и телефон отмечайте проверенными только по фактическому результату.

Если телефон недоступен агенту, дайте владельцу адрес сайта и короткую последовательность проверки. Не считайте развёртывание полностью проверенным до подтверждения недоступных агенту действий.

## 8. Передайте результат

Сообщите постоянный адрес сайта, настроенные сервисы, выполненные проверки и оставшиеся действия. Не включайте секреты, содержимое библиотеки и подписанные ссылки B2.

Объясните статус отправки и автоматическую синхронизацию при открытом приложении. Укажите, что закрытая вкладка не синхронизируется, неотправленные изменения хранятся только на устройстве, а без сети доступны только кешированные идеи и вложения. Очистка данных сайта не удаляет облачные записи. Экспорт и импорт собирают полную библиотеку; подтверждённая очистка получает только записи и описания вложений, без скачивания оригиналов. Дайте ссылку на [резервные копии](../README.md#резервные-копии).

При остановке оставьте краткий список выполненного и следующего шага без секретов, чтобы работу можно было продолжить без повторной настройки. Для ошибки укажите этап, безопасный текст сообщения и способ проверки. Если требуется разрешение или действие владельца, объясните конкретную причину.
