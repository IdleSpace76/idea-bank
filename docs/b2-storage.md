# Хранение библиотеки в Backblaze B2

Реализованы серверный API и ручная синхронизация интерфейса. Локальная копия хранится в браузере; отправка и получение облачных изменений запускаются кнопкой **Синхронизировать**. Автоматической фоновой синхронизации нет.

GitHub хранит открытый код приложения и используется для входа владельца. Все пользовательские данные — тексты и медиа — хранятся вместе в закрытом B2 bucket. Vercel запускает приложение и серверные обработчики. Закрытый репозиторий GitHub для данных не требуется.

## Настройки личной копии

1. Создай собственный аккаунт [Backblaze B2](https://www.backblaze.com/sign-up/cloud-storage) без карты. На момент проверки первые 10 ГБ хранения бесплатны; операции и скачивания также имеют свои условия. Проверяй [актуальные тарифы](https://www.backblaze.com/cloud-storage/pricing), не добавляй платёжный метод, если нужен режим без списаний.
2. Создай bucket с **Private**, включённым шифрованием и выключенным Object Lock. Сохрани имя и S3 Endpoint. Регион, например `eu-central-003`, виден в endpoint.
3. Создай Application Key: доступ **только к этому bucket**, **Read and Write**, без префикса. `Allow List All Bucket Names` не нужен. Не используй master key.
4. Добавь в `.env.local` (или серверные Environment Variables на хостинге):

   ```dotenv
   B2_S3_ENDPOINT=https://s3.eu-central-003.backblazeb2.com
   B2_REGION=eu-central-003
   B2_BUCKET_NAME=имя-твоего-bucket
   B2_KEY_ID=keyID
   B2_APPLICATION_KEY=applicationKey
   ```

5. Вход владельца должен быть настроен по [github-login.md](github-login.md): `IDEA_BANK_AUTH_MODE=github`. В локальном режиме без аккаунта облачные endpoints закрыты.

Ни одна из этих переменных не должна иметь префикс `NEXT_PUBLIC_`. Секреты не передаются клиенту и не включаются в исходники. После изменения переменных перезапусти сервер; на хостинге выполни новый deployment.

Для загрузки из браузера настрой CORS. Команда без `--apply` только проверяет; с ним добавляет собственное правило для текущего `AUTH_URL`, сохраняя другие правила и Private-доступ:

```sh
npm run storage:cors
npm run storage:cors -- --apply
```

Ключу нужна возможность `readBuckets`/`writeBuckets` для этого bucket. Правило разрешает точный origin приложения, GET/PUT/HEAD и заголовки `content-type`, `content-md5`, `x-amz-meta-sha256`. Для локального запуска origin — `http://127.0.0.1:3000`. После развёртывания добавь production-origin той же командой с корректным `AUTH_URL`; localhost/127.0.0.1/разные порты — разные origins. Сам API B2 остаётся закрыт подписанными ссылками; CORS не открывает bucket посторонним.

## Формат данных и конфликты

- `idea-bank/v1/revisions/<родители>_<uuid>.json` — отдельные снимки библиотеки с `library`, списком вложений `media`, `revision`, `parents` и `createdAt`.
- `idea-bank/v1/media/<sha256>-<md5>` — медиа, адресуемые по содержимому. Имена пользовательских файлов хранятся в библиотеке, не используются как пути объектов.
- Вложения загружаются раньше снимка библиотеки. Перед записью сервер проверяет их наличие, размер, MIME, метаданные SHA-256 и MD5/ETag.
- SHA-256 рассчитывается клиентом. B2 проверяет подписанный `Content-MD5` при загрузке; повторное скачивание всех файлов на сервер ради пересчёта SHA-256 не выполняется.
- Сохранение содержит список `baseRevisions` — версии, на основе которых пользователь редактировал данные. При несовпадении с актуальными вершинами истории сервер отвечает **409 CONFLICT**.
- Если два запроса успели проверить одну и ту же базу одновременно, создаются две ветки. Ни одна версия не перезаписывается. Последующие чтения выявляют конфликт; нельзя молча выбрать «последнюю» ветку. Успешный ответ одного запроса не исключает появления второй ветки немного позже.
- Разрешение конфликта: прочитать обе версии по ID, подготовить объединённую библиотеку и сохранить её с полным актуальным списком `baseRevisions`. Новый снимок ссылается на обе исходные версии. В интерфейсе можно явно выбрать локальную библиотеку или одну из облачных веток как новую общую версию. Автоматического объединения текста по строкам пока нет.

Снимки не удаляются автоматически. Не настраивай lifecycle-правила, которые удаляют целиком объекты из `idea-bank/v1/revisions/`: потеря родителя ломает цепочку истории. Старые медиа пока тоже не удаляются — они могут быть нужны предыдущим снимкам. Очистка истории и неиспользуемых файлов потребует отдельного шага; экспорт ZIP остаётся независимой резервной копией.

## API

Все ответы имеют `Cache-Control: private, no-store`. Нужна сессия владельца; для PUT/POST также обязателен `Origin`, точно совпадающий с `AUTH_URL`. Неавторизованные запросы получают 401, запросы записи с другого origin — 403. Отсутствующие настройки B2 дают 503. Неизвестные ошибки B2 возвращаются как 502 без SDK-деталей и ключей.

| Метод и адрес | Назначение |
| --- | --- |
| `GET /api/storage/library` | Последняя единственная версия `{snapshot, heads}`; пустое хранилище — `{snapshot:null, heads:[]}`; при ветках — 409 со списком `error.revisions`. |
| `GET /api/storage/library?revision=<uuid>` | Конкретная версия, включая ветку конфликта. |
| `PUT /api/storage/library` | JSON `{baseRevisions:[], library, media:[]}`. Для обычного обновления — один родитель, для разрешения конфликта — все актуальные вершины. |
| `POST /api/storage/media/upload` | JSON `{id,sha256,md5,size,mime}`. Возвращает `{alreadyUploaded,media}` либо дополнительно `{url,method,headers,expiresIn}`. |
| `GET /api/storage/media/download?revision=<uuid>&id=<media-id>` | Подписанная ссылка на файл, упомянутый в указанном снимке. |

После получения upload URL браузер отправляет исходный Blob методом PUT прямо в B2 с **точно возвращёнными заголовками**. Content-Length вычисляет браузер по Blob; размер тоже входит в подпись. SHA-256 — 64 строчных hex-символа, MD5 — 32. MD5 используется для совместимости и проверки передачи, не как единственный идентификатор файла.

Ссылки действуют **5 минут** и дают доступ к одному объекту. Скачивать по ним может любой, кому передали ссылку, до её истечения. Выход из приложения не отзывает уже выданные ссылки немедленно. Не сохраняй ссылки в библиотеку и не публикуй их в логах.

Ограничения текущей серверной реализации: JSON-запрос и снимок до **3 МиБ** (медиа передаются отдельно), один медиафайл до **1 ГиБ**, история до **10 000 снимков**, до **16 родителей** одного объединения. Это отдельные ограничения от лимита ZIP-резервной копии. Автоматического multipart upload и возобновления больших загрузок пока нет.

## Проверки

```sh
npm run build
npm run test:storage
npm run test:auth
npm run test:sync
```

`test:storage` проверяет формат, отсутствующие вложения, устаревшие записи, параллельные ветки, их объединение и подписанные ссылки на тестовом хранилище в памяти. `test:auth` проверяет реальные серверные endpoints без доступа к B2: запрет анонимных/чужих сессий и стороннего Origin, размер и формат тела.

Для проверки собственных рабочих ключей отдельно:

```sh
npm run test:storage -- --live --browser
```

Live-проверка создаёт только временные объекты в уникальной папке `idea-bank-check/<uuid>/`, проверяет загрузку, скачивание, сохранение JSON и контрольную сумму. Затем удаляет именно эти объекты вместе с версиями. `idea-bank/v1/` не изменяется. При прерванной проверке папка может остаться — её можно удалить через консоль B2. Тест не выводит ключи или подписанные ссылки.

Документация: [B2 S3 API и presigned URLs](https://www.backblaze.com/docs/cloud-storage-s3-compatible-api), [CORS](https://www.backblaze.com/docs/cloud-storage-cross-origin-resource-sharing-rules).

## Первый перенос и работа с копиями

1. Перезапусти приложение после настройки ключей. Войди владельцем и сохрани/отмени открытые правки.
2. Нажми **Синхронизация** вверху либо **Синхронизация и копии** внизу → **Синхронизировать**.
3. При первом подключении выбери направление: **Сохранить локальную в облаке** либо **Загрузить облачную на устройство**. Будут показаны количество и названия идей. Перед заменой непустой локальной библиотеки можно экспортировать ZIP.
4. На другом устройстве открой этот же опубликованный HTTPS-адрес приложения, войди и получи облачную библиотеку. Идеи и все медиа скачиваются на устройство; в уже открытом приложении их можно просматривать без связи. Для нового открытия или перезагрузки сайта нужна сеть. После офлайн-правок нажми синхронизацию при восстановлении связи.
5. Если только устройство изменилось — кнопка отправляет правки. Если изменилось только облако — получает их. Если изменились обе стороны или найдены ветки — приложение просит выбрать версию. Выбор создаёт новую облачную версию, старые остаются в истории.

Новые загрузки проверяются по SHA-256/MD5, записываются в IndexedDB под свежими ID и только затем заменяют локальную библиотеку. Обложки и общие ссылки внутри блоков сохраняются. Повторно доступные локальные файлы используются после проверки хеша. Файлы для отправки хешируются потоково; при скачивании в памяти находится один файл, не вся библиотека. Для временного сохранения новых файлов нужно дополнительное место на устройстве.

Ключ `idea-bank.cloud.v1` хранит привязку к экземпляру хранилища, базовую версию, хеш библиотеки, дату синхронизации и карту файлов. Подписанные URL и ключи B2 в браузерное хранилище не записываются. Журнал незавершённого переключения восстанавливается при запуске или перед следующей локальной записью. Импорт ZIP и загрузка Example остаются локальными изменениями до ручной синхронизации.

`test:sync` запускает два независимых браузерных профиля с подменённым облачным API и проверяет перенос точных байтов изображения/модели/обложки, повторную синхронизацию, отсутствие сети, конфликт, повреждённый файл, изменение в другой вкладке, нехватку места и восстановление журнала. Live-проверка с `--browser` дополнительно выполняет настоящие PUT/GET из браузера с origin `AUTH_URL`, проверяя CORS, и удаляет временные файлы.
